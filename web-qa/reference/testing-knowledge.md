# 测试工作内容与流程 · 知识库

> 这是 `/web-qa` skill 的背景知识。既是执行测试时的方法论依据，也可单独当作"测试岗在做什么"的学习资料。
> 来源综合自 ISTQB 体系 + 行业现行实践（2025–2026）。

---

## 一、测试岗到底在做什么（职责全景）

测试工程师（QA / Test Engineer）的核心使命：**在产品交付给用户前，用系统化方法找出它"会坏"的地方，并推动修复，给"能不能发布"提供事实依据。**

按时间线展开，日常工作分 6 块：

1. **需求分析与评审** — 读 PRD / 设计稿，找出歧义、漏洞、自相矛盾的需求。好的测试在写代码前就开始（shift-left，左移测试），需求阶段发现的问题修复成本最低。
2. **测试计划（Test Plan）** — 定范围、定策略、定优先级、定环境、定通过标准（exit criteria）。回答"测什么、不测什么、怎么测、什么算通过"。
3. **测试用例设计（Test Case Design）** — 把需求拆成一条条可执行、可判定的用例。用例 = 前置条件 + 操作步骤 + 测试数据 + 预期结果。这是最体现专业度的一步（见第三节技巧）。
4. **测试执行（Execution）** — 手工点 / 跑自动化脚本，对照预期判定 pass/fail，记录证据。
5. **缺陷管理（Defect Management）** — 发现 bug → 提单（可复现步骤 + 预期 vs 实际 + 严重级别 + 证据）→ 跟踪到关闭 → 回归验证。
6. **报告与质量度量** — 输出测试报告、覆盖率、缺陷分布、风险评估，最终给"ship / no-ship"建议。

## 二、软件测试流程（STLC，Software Testing Life Cycle）

标准 6 阶段，和开发 SDLC 并行：

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 1. 需求分析 | 理解被测对象、判断可测性、识别测试类型 | 可测性报告、测试范围 |
| 2. 测试计划 | 定策略/资源/排期/风险/通过标准 | Test Plan |
| 3. 用例设计 | 设计用例、准备测试数据、搭测试环境 | 用例集、测试数据 |
| 4. 环境搭建 | 准备被测环境（可与 3 并行） | 就绪的测试环境 |
| 5. 测试执行 | 执行用例、记录结果、提缺陷、回归 | 执行记录、缺陷单 |
| 6. 测试收尾 | 评估出口标准、总结、归档 | 测试报告、经验沉淀 |

**关键概念：**
- **Entry / Exit Criteria（进入/退出标准）**：什么条件才开始测、什么条件才算测完。例如出口标准 = "P0/P1 缺陷全部关闭，核心用例通过率 100%，回归通过"。
- **Shift-left（左移）**：把测试尽量往研发早期推，需求/设计阶段就介入，越早发现越省钱。
- **Shift-right（右移）**：上线后用监控、灰度、A/B、真实流量继续验证（线上质量）。

## 三、测试用例设计技巧（黑盒，最常用）

不可能穷举所有输入，所以用这些技巧"用最少用例覆盖最多风险"：

1. **等价类划分（Equivalence Partitioning）** — 把输入分成"行为相同的组"，每组取一个代表值测。例：年龄字段 0–120 有效，则 `[<0]`、`[0–120]`、`[>120]` 三个等价类各取一个。
2. **边界值分析（Boundary Value Analysis）** — 错误最爱藏在边界。对每个边界测 `min-1, min, min+1, max-1, max, max+1`。和等价类配合用，覆盖率最高。
3. **判定表（Decision Table）** — 多个条件组合影响结果时，列全条件×动作的组合，避免漏组合。
4. **状态迁移（State Transition）** — 有状态的系统（登录态、订单状态机），测合法迁移 + 非法迁移。
5. **错误猜测（Error Guessing）** — 基于经验主动猜"哪里容易坏"：空值、超长、特殊字符、并发、断网、重复提交、负数、0、超大数。
6. **正交/成对组合（Pairwise）** — 多参数组合爆炸时，用成对覆盖大幅压缩用例数。

**每条好用例必备 4 要素：** 前置条件、操作步骤、测试数据、明确可判定的预期结果。预期结果必须具体（"显示红色错误提示『邮箱格式不正确』"），不能是"应该正常"。

## 四、测试类型（按维度）

### 按是否运行程序
- **静态测试**：评审、代码走查、静态扫描（不运行）。
- **动态测试**：真正运行程序去测。

### 按是否看代码
- **黑盒**：只看输入输出，不管内部实现（功能测试为主）。
- **白盒**：看代码逻辑，覆盖分支/路径/语句。
- **灰盒**：两者结合（比如知道接口结构去测 API）。

### 按测试目标（Web 产品最关心的）

**功能性（Functional）**
- **功能测试**：每个功能符合需求。
- **冒烟测试（Smoke）**：核心链路通不通，发布前第一道关。
- **回归测试（Regression）**：改了 A 没把 B/C 搞坏。改动后必跑。
- **端到端（E2E）**：模拟真实用户走完整业务流程。

**非功能性（Non-functional）**
- **可用性 / UX**：好不好用、流程顺不顺、文案清不清楚。
- **兼容性**：不同浏览器（Chrome/Safari/Firefox/Edge）、设备、分辨率、系统版本。
- **响应式**：手机/平板/桌面各断点布局是否正常。
- **性能**：加载速度、响应时间、并发、Core Web Vitals（LCP/CLS/INP）。
- **安全**：鉴权、越权、XSS、SQL 注入、敏感信息泄露、CSRF。
- **可访问性（a11y）**：WCAG 合规、键盘可达、对比度、屏幕阅读器、alt 文本。

**其他**
- **接口/API 测试**：绕过前端直接测后端契约、状态码、边界。
- **探索性测试（Exploratory）**：无脚本，靠经验边玩边测，最易发现意外 bug。

## 五、缺陷（Bug）管理

### 一条合格 bug 单包含
1. **标题**：一句话点出问题（页面 + 现象）。
2. **环境**：URL / 浏览器 / 设备 / 账号 / 版本。
3. **复现步骤**：编号、可被任何人照着复现。
4. **预期结果 vs 实际结果**：对比清楚。
5. **证据**：截图、录屏、console 报错、网络请求。
6. **严重级别 + 优先级**。
7. **复现率**：必现 / 偶现（附概率）。

### 严重级别（Severity）— 问题对系统的破坏程度（技术视角）
| 级别 | 含义 | 例子 |
|---|---|---|
| **Critical / S1** | 系统崩溃、数据丢失、核心功能完全不可用、阻塞 | 无法登录、支付失败、页面白屏 |
| **High / S2** | 主要功能受损、无合理绕过方式 | 提交按钮无响应、关键数据显示错误 |
| **Medium / S3** | 次要功能问题、有绕过方式 | 某筛选器失效、个别校验缺失 |
| **Low / S4** | 轻微/外观问题 | 文案错别字、对齐偏移、间距不一致 |

### 优先级（Priority）— 多急着修（业务视角）
- **P0**：立刻修（阻塞发布）。**P1**：本次发布必修。**P2**：可排期。**P3**：有空再说。

**关键区别：** Severity 看"坏得多狠"，Priority 看"多急着修"。两者可错位 —— 比如"公司 LOGO 拼错"严重级别低（不影响功能）但优先级高（影响品牌，要马上改）；"某冷门导出格式偶尔报错"严重级别高但优先级可能低。判级要基于真实影响，别凭"看起来多吓人"。

## 六、Ship / No-ship 判定

测试最终要回答"能不能发"。给结论时基于事实：
- **可发布**：P0/P1 全清，核心用例 100% 通过，回归通过。
- **带风险发布**：仅剩低优先级问题，列清已知问题清单（known issues）。
- **不可发布**：存在未解决的 P0/P1，说明阻塞点。
