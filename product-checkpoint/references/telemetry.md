# 埋点设计原则 · Telemetry Design

> P4 telemetry 和 P6 调优循环的核心方法论。
> 在 phase self-check 中被引用，回答"事件该不该埋、在哪埋、怎么设计"。

---

## 一句话本质

埋点 = **把产品里发生的每一件事，翻译成可统计的事件**，让产品决策从"凭感觉"变成"有据可查"。

## 它解决的根本问题

**用户说的 ≠ 用户做的。**

- 用户访谈拿到的是"他记忆中 / 想象中的自己"
- 埋点拿到的是"他真实做了什么"
- 两个不一致时永远信埋点

没埋点 → 你只能用"我觉得 / 老板觉得"做决策 → 永远走不出"我以为用户喜欢这个 feature 但其实没人用"的循环。

这是俞军《产品方法论》第 2 章「用户是需求的集合」的工程化版本：埋点把"自然人"切成"行为序列"，每条事件 = 一次具体情境下的需求触发。

---

## 核心思维：问题驱动，不是事件驱动

**❌ 错误顺序**（90% 团队的做法）：
能埋什么 → 全埋 → 几个月后看 → 数据墓地 → 没人用

**✓ 正确顺序**：
**先列要回答的决策问题 → 反推需要哪些事件 → 反推每个事件需要哪些属性 → 才动手埋**

| 决策问题 | 推出的事件 |
|---|---|
| "用户在哪一步掉？" | 漏斗各节点 view / submit |
| "改 prompt 后用户读得更深吗？" | `generation_completed` 带 `prompt_version` + `result_dwell` |
| "重度用户在赚我钱还是赔我钱？" | `generation_completed` 带 `cost` + 用户 lifetime events |
| "新版本上线后转化率怎么变？" | 关键事件带 `release_version` |

**事件本身不重要，能回答的问题才重要。**

上线前自问：「**不埋这个我无法回答什么问题？**」答不上 → 不埋。

## 一个事件长什么样：5W1H

每条事件 = 一行回答 「谁，什么时候，干了什么，在哪里，怎么干的，因为什么」 的数据：

```json
{
  "event": "result_shared",            // WHAT
  "timestamp": "2026-05-21T03:14:22Z", // WHEN
  "user_id": "anon_a8f3",              // WHO
  "session_id": "s_2k3l",              // WHO（细一级）
  "page": "/result/r_123",             // WHERE
  "referrer": "/setup",                // WHY
  "properties": {                      // HOW
    "share_channel": "wechat",
    "model_version": "claude-4-7",
    "prompt_version": "v3.2",
    "dwell_before_share_ms": 28000
  }
}
```

## 客户端 vs 服务端

### 最直白的区分

**代码跑在哪台机器上？**

- **客户端 client** = 跑在**用户手里那台机器**上的代码（浏览器、手机 app）
- **服务端 server** = 跑在**你公司控制的机器**上的代码（云服务器、Netlify、AWS）

```
[用户的浏览器: 客户端] ←HTTPS→ [你的 server: 服务端] ←HTTPS→ [外部 API / 模型]
       ↑                              ↑                              ↑
   用户控制                       你控制                          供应商控制
```

### 各自能埋什么

| 类型 | 客户端 | 服务端 |
|---|---|---|
| 鼠标点击 / 滚动 / 视口 | ✓ 只有这里能埋 | ✗ 看不到 |
| 页面停留时长 / 截屏 | ✓ 只有这里能埋 | ✗ 看不到 |
| 表单填了一半就退出 | ✓ 只有这里能埋 | ✗ 用户没提交，服务端不知道 |
| 设备信息 / 浏览器 | ✓ 只有这里能埋 | △ 能从 User-Agent 推断 |
| API 请求耗时 | △ 用户感知延迟 | ✓ 精确知道 |
| 数据库 / 模型调用 token | ✗ 看不到 | ✓ 只有这里能埋 |
| **真实付款完成** | ✗ **不可信** | ✓ **必须这里埋** |
| 业务错误 / 模型失败 | △ 只看到用户看到的 | ✓ 精确知道哪一步死了 |

### 可信度差异（最重要的一点）

**客户端**（中等可信）：
- ❌ 用户可以装广告拦截器 → 你的埋点 SDK 被屏蔽
- ❌ 用户可以关 JavaScript → 完全没数据
- ❌ 网络中断 → 数据丢失你也不知道
- ❌ 用户能改开发者工具伪造事件
- ✓ 但能看到用户视觉行为，这是服务端永远看不到的

**服务端**（高可信）：
- ✓ 数据是你自己代码写的，100% 可信
- ✓ 不会被屏蔽 / 拦截
- ✓ 关键业务事件（付款、订单）**必须**在这埋
- ❌ 但看不到用户实际看到 / 感知 / 滚动的东西

### 判断公式

1. 关键业务事件吗？（付款、订单、用户身份变更）→ **必须服务端**
2. 用户在浏览器里的视觉 / 行为事件吗？（点击、滚动、停留、视口）→ **只能客户端**
3. 后端处理过程吗？（API 调用、模型推理、错误）→ **必须服务端**
4. 都可以的事？（如 page view）→ **服务端优先**

**铁律**：能服务端埋就别在客户端。但视觉行为只能客户端埋。

## Event Sourcing · "事件不可变" 是什么意思

### 最好的类比：银行账户

银行**不会**存一行"小明现在余额 ¥5000"。它存的是**事件流**：

```
2026-01-01  存入  +1000
2026-01-15  取出  -300
2026-02-01  存入  +4300
```

余额 ¥5000 是**算出来的**，不是**存着的**。

这就是 event sourcing：**状态由事件序列推导，状态不直接存**。

### 为什么这样做

| 好处 | 例子 |
|---|---|
| **审计追溯** | 每一分钱怎么来怎么去全能查 |
| **不会丢真相** | 哪怕状态算错了，重跑事件就能复原 |
| **能时光旅行** | 能算"3/1 时余额多少" → 累加 3/1 前的事件 |
| **逻辑变了能重算** | 改了"会员等级算法"后，重新跑老事件得出新结论 |

### 应用到产品埋点

**❌ 错的做法**（把状态存进 events 表）：
```
events 表新增一列 is_paid_user
用户付费时把这一列改成 true
退款时改回 false
```

问题：
- 失去了"用户什么时候付的、什么时候退的、付了几次、每次付多少"的信息
- 这一列是 mutable 的，可能被改坏 / 误删
- 半年后想问"3 月有多少新付费"，根本算不出

**✓ 对的做法**（只存事件，状态推导）：
```
events 表里只有事实：
  2026-03-01 payment_completed user_42 amount=29
  2026-03-15 subscription_cancelled user_42
  2026-04-01 payment_completed user_42 amount=29
```

"用户 42 是不是付费用户？" → 查最近一次 `payment_completed` 是否在有效期内 → **推导**出来。

### 核心区分

| 层 | 性质 | 例子 |
|---|---|---|
| **事件流** | 不可变 · 是事实 · append-only | "小明在 X 时刻付了 ¥29" |
| **派生状态** | 可重算 · 是视图 · 可能错 | "小明现在是付费用户" |

PM 设计埋点最容易犯的错：「我加一个 `has_used_quiz` 字段就行」——这是把状态当事件埋。

**正确思维**：只埋"发生了什么"（`quiz_completed`），让分析时去推导状态（`SELECT DISTINCT user_id FROM events WHERE event='quiz_completed'`）。

这样埋点能回答**未来还没想到的问题**——半年后老板问"用过 quiz 又付费的用户停留了多久"，你能从事实重新拼出来。如果只存 `has_used_quiz=true`，再也算不出"什么时候用的、用了几次"。

## 5 条不可妥协的原则

1. **事件不可变（append-only）** — events 表只追加不更新。"用户当前是付费"这种**状态**不进 events，是从事件序列推导出来的

2. **Schema 治理 > 一次性正确** — 命名规范从 day 1 定死：`snake_case` + `verb_noun` 谓宾结构（如 `cta_clicked` 不要叫 `click_event_001`）。其它细节可以慢慢补，命名乱了一辈子改不回来

3. **AI 产品必带 version** — `prompt_version` + `model_version` 是 AI 事件的"出生证"。少一个字段，跨版本对比就废了——"改 prompt 后效果跌了 30%" 永远说不清是 prompt 改坏了还是流量变了

4. **隐私第一** — 用户原文不进 events，只存**哈希 / 长度 / boolean**。例：不要存"林夏"，存 `{"has_name": true, "name_length": 2}`

5. **每个事件配一个问题** — 上线前自问"不埋这个我无法回答什么问题？"答不上 → 不埋

## 5 个常见反模式

| 反模式 | 后果 |
|---|---|
| **埋越多越好** | 数据墓地，noise 淹没 signal，维护成本爆炸 |
| **只埋客户端** | 漏斗中段大段数据缺失，用户被广告拦截后你完全瞎 |
| **没 version 字段** | 改 prompt 后跌 30%，永远说不清原因 |
| **埋了用户原文 / PII** | 合规炸弹，撤回成本极高 |
| **用埋点代替用户访谈** | 数据告诉你"在哪掉"，但不会告诉你"为什么"——必须互补 |

## AI 产品**必须**在每个 generation 事件上带的字段

普通 SaaS 不需要、AI 产品躲不开：

```json
{
  "prompt_version": "v3.2",         // 关键！否则 A/B 对比不了
  "model_version": "claude-4-7",    // 换模型时数据可以分开看
  "input_tokens": 850,
  "output_tokens": 2400,
  "latency_ms": 8200,
  "cost_cny": 0.038
}
```

只要这 6 个字段稳定埋着，未来能算：
- v3.1 vs v3.2 哪个用户读完率高
- 换 Haiku 后掉了多少质量
- 重度用户每月让你亏多少
- 哪个 prompt 在哪个用户群上表现最好

**少埋一个字段都算不出。**

## 跟 7-Phase 流程的关系

| Phase | 跟埋点的关系 |
|---|---|
| **P4 MVP 工程** | telemetry day 0 必须有。没埋 = 飞行没仪表盘 |
| **P5 首批真实用户** | 看用户行为（视觉行为）必须有客户端埋点 |
| **P6 调优循环** | 没埋 prompt_version + 质量信号 → 调优变成体感 |
| **P7 Unit Economics** | 没埋 cost / token / 按 cohort 的 events → 算不出回本点 |

**埋点设计错误 = 后面 P5/P6/P7 全部退化为体感。**

---

## 一句话结尾

> **埋点的本质，是让你的产品直觉「有可能被证伪」**。
>
> 没埋点的决策永远是"我觉得"；有埋点的决策才有"我错了，得改"的可能性。
>
> 这跟做科学实验的逻辑一样——假设 → 数据 → 修正假设。没有数据的产品决策，本质上是占卜不是产品工程。
